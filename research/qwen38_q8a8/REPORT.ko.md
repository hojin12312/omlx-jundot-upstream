## B. 기존 Q8 경로 조사

- 체크포인트의 모든 선형 투영은 8비트, GS64, affine, 메타데이터 BF16입니다(임베딩과 `lm_head`도 8비트).
- 모델 형태: GDN 48층 + 전체 어텐션 16층, hidden 5120, MLP 중간 17408.
- 주요 투영 (K, N): MLP gate/up (5120, 17408), down (17408, 5120), GDN qkv (5120, 10240), z (5120, 6144), out_proj (6144, 5120), `in_proj_a/b` (5120, 48), 어텐션 q (5120, 12288), k/v (5120, 1024), o (6144, 5120).
- 이 체크포인트는 VLM 엔진(`VLMBatchedEngine`)으로 로드됩니다.
- 순정 main, 기본 설정, 카운터만 수집한 실행(`route_counters.json`)의 결과입니다.
  - production prefill 청크는 2048행입니다(1K 프롬프트는 한 청크, 이후 2048 단위).
  - 기존 Q8 A16 네이티브 QMM 호출은 모든 길이에서 0회입니다. 청크당 stock 투영이 497회(`lm_head` 1회 포함)입니다. 이슈 #3506(Q8 임계값 16384가 청크 2048에 도달하지 못함)이 이 모델에서 그대로 재현됩니다.
  - 마이크로벤치에서 oMLX 네이티브 Q8 A16(NAX)은 stock MLX와 같은 속도(±1%)입니다. 즉 #3506을 임계값만 낮춰 해결해도 속도 이득이 없습니다.
  - `lm_head`는 청크 전체 행(2048행)에 대해 매 청크 실행됩니다. prefill 연산의 약 5%이며 이번 범위에서는 건드리지 않았습니다.
- 주의: VLM 엔진에서는 GDN 입력 투영이 공유 Stage A 경로(`oq_a8_gdn_projections`)에 도달하지 않습니다. qkv와 z는 각자 Stage A를 수행하고 `in_proj_a/b`(N=48, 타일 미충족)는 stock으로 남습니다. 공유했을 때의 절감은 청크당 0.2% 미만이라 제품 diff에서 부분 공유 코드를 제거했습니다.

## C. 설계

- 수식(소스와 실험으로 검증): MLX affine은 `w = scale * q_u8 + bias`이고 q는 부호 없는 바이트(리틀 엔디언)입니다. 바이트의 최상위 비트를 뒤집으면 `q - 128`(INT8)이 되며,
  `sum_k a_k w_k = scale * (acc + 128 * r) + bias * r` (GS64 그룹마다, acc는 INT32 텐서 연산 결과, r은 Stage A가 이미 만드는 그룹 합)입니다. `acc`와 `128 * r`는 2^24보다 훨씬 작아 FP32 합이 정확합니다. 경계 코드 0, 127, 128, 255와 FP16/BF16 메타데이터에서 float64 기준과 일치합니다.
- 커널: 새 파일 `qwen35_oq_q8_a8_nax.metal`. 기존 Q4/Q5 커널 소스는 수정하지 않았습니다. Q8 바이트는 한 단계에 워드 하나이므로 활성화를 체크포인트 순서 그대로 읽는 "natural" 레이아웃을 씁니다. Stage A v8의 순열 복사가 없고, 순열 레이아웃에 비해 GEMM이 약 11% 빠릅니다. unpacked 가중치 행렬은 만들지 않습니다.
- Stage A 재사용: MLP는 gate/up이 Stage A를 한 번 공유하고 down은 자기 입력을 양자화합니다(청크당 Stage A 336회, A8 투영 400회).
- 활성화 스케일: 기본값은 GS64(그룹별 스케일, `OMLX_OQ_A8_Q8_ACT_MODE=1`)입니다. 행 단위 스케일은 품질 게이트에 실패했습니다(아래 F).
- 라우팅: `qwen35_q4_mlp.py`에서 8비트 투영이 A16 임계값 16384 아래에서도 A8 백엔드에 먼저 제안됩니다(행 수 64 이상일 때만). 백엔드가 거절하면 stock 경로로 가며 Q8 A16 타일로는 가지 않습니다. 사용자 설정은 기존 `qwen35_oq_a8_enabled`와 `qwen35_oq_a8_min_tokens`를 그대로 씁니다.
- 기존 Q4/Q5 영향: 고정 입력에서 Q4/Q5 A8 출력 216개가 순정 main 빌드와 src 빌드에서 비트 단위로 동일합니다(`research/q45_identity.py`).

## D. 마이크로벤치 (M=32..8192, 실제 체크포인트 가중치)

GS64 기본값 기준 전체 표는 `micro_table_g64.md`, 행 단위 스케일 표는 `micro_rowscale.jsonl`에 있습니다. 정확성 검증(합성 280케이스, 7개 타일, 2 스케일 모드, 2 dtype, 꼬리 M, 경계 코드)에서 디코더 오차는 출력 반올림 수준이고 활성화 양자화 오차는 상대 L2 약 0.6%입니다.

요약(GS64, Stage A 포함, stock MLX 대비):

| shape | M=512 | M=2048 |
|---|---:|---:|
| MLP gate/up | +45.5% | +39.3% |
| MLP down | +21.7% | +24.4% |

M>=512 전체 구간에서 stock 대비 이득은 최소 +2.0%(k/v, N=1024), 중앙값 +34.7%, 최대 +48.0%입니다. M=64 이하는 이득이 작습니다.

## E. 전체 모델 prefill (같은 서버, 같은 요청 바이트, 순서 교대, settle 10초, 길이별 6쌍)

GS64 기본값(최종):

| 프롬프트 | off | Q8A8 | 짝지은 이득 | TTFT |
|---|---:|---:|---:|---|
| 1K | 846 tok/s | 1103 tok/s | +30.3% | 1.21 -> 0.93 s |
| 4K | 951 | 1244 | +30.9% | 4.31 -> 3.29 s |
| 8K | 695 | 983 | +42.1% | 11.8 -> 8.3 s |
| 16K | 692 | 960 | +38.7% | 23.7 -> 17.1 s |
| 32K | 665 | 903 | +36.1% | 49.3 -> 36.3 s |

모든 쌍에서 Q8A8이 빨랐습니다(길이마다 6/6). 행 단위 스케일(품질 실패, 참고용)은 +41/+46/+59/+57/+52%입니다.

측정 편향 점검 기록:
- 첫 스모크(settle 1.5초)의 4K 이득 +55~63%는 과대평가였습니다. off 팔이 열로 눌렸기 때문이며, settle 10초에서 off가 958 tok/s로 회복되었습니다. 조건 대칭 A/A(`off` 대 `off2`)는 평균 +0.11%였습니다.
- 별도 서버 프로세스 ABBA(순정 main 설정 off 대 src 설정 on)도 같은 방향이었습니다(행 단위 스케일 기준 4K 1.50배, 16K 1.63배). 단, main 프로세스 기준선이 617~931 tok/s로 크게 흔들려 정밀 수치로는 쓰지 않았습니다.
- 8K 이상에서 행 단위 스케일 이득(+57~59%)은 GEMM 단독 상한(약 1.54배)을 넘었습니다. 기준선의 열 상태 영향이 섞였을 가능성이 있어 보수적으로 settle 10초 프로세스 내 교대 값만 최종 수치로 삼았습니다.
- 기존 Q8 A16 네이티브 QMM을 2048행 임계값으로 강제한 대조군(`a16`)은 off와 같은 속도였습니다(4K에서 +2.9% 이내). 즉 이득은 임계값 문제가 아니라 W8A8 자체에서 나옵니다.

## F. 품질 (같은 Q8 체크포인트, A16 활성화 기준 대 A8 활성화, 36개 시퀀스 163,840 위치, 청크 2048)

| 방식 | ΔNLL (95% CI) | PPL 비율 | top-1 일치 | 평균 KL | greedy 24토큰 동일 |
|---|---|---:|---:|---:|---:|
| 행 단위 스케일 | -0.0615 (-0.107, -0.016) | 0.940 | 0.861 | 0.839 | 10/36 |
| GS64 스케일(기본값) | -0.0021 (-0.0062, +0.0019) | 0.998 | 0.945 | 0.222 | 22/36 |

- 대조군(A16 대 A16)은 KL 최대 0으로 하네스 잡음이 0임을 확인했습니다. NaN과 Inf는 없습니다.
- 행 단위 스케일은 평균 ΔNLL이 음수로 나왔지만 구조화 시퀀스에서 분포가 크게 어긋났습니다(KL 3~4.6). 활성화 이상치를 행 전체 스케일이 담지 못하는 것으로 해석하며, 기본값으로 채택하지 않았습니다.
- GS64 스케일 범주별(ΔNLL / 평균 KL / top-1): 영어 +0.0004 / 0.0020 / 0.977, 한국어 -0.0010 / 0.0014 / 0.974, 코드 +0.0017 / 0.0019 / 0.988, 긴 산문 +0.0001 / 0.0017 / 0.981, 스키마 코드 +0.0004 / 0.0011 / 0.991, 추론형(합성) +0.0003 / 0.047 / 0.892, 도구 호출형 transcript -0.0093 / 1.40 / 0.821, 에이전트 -0.0065 / 0.75 / 0.873, JSON 응답 -0.0076 / 0.0092 / 0.975.
- 공개해야 할 한계: 전체 KL 질량의 95%가 KL>1인 위치 2.4%(주로 도구 호출형, 에이전트, 합성 시퀀스의 특정 위치)에서 나옵니다. 이 범주는 평균 KL과 top-1이 나쁘지만 ΔNLL은 0 근처이거나 음수입니다. 도구 호출 구조 유효성 스모크는 아직 하지 않았습니다.

## G. 메모리 (프로세스 분리, off/on/on/off, 2회 반복 일치)

| 항목 | off | on | 차이 |
|---|---:|---:|---:|
| 로드 직후 active | 27.942 GiB | 27.942 GiB | 0 |
| 첫 prefill 이후 settled | 27.942 GiB | 29.358 GiB | +1.416 GiB |
| 16K prefill 최대 | 32.466 GiB | 33.875 GiB | +1.409 GiB |
| 32K prefill 최대 | 33.443 GiB | 34.904 GiB | +1.461 GiB |

- 상주 증가분 +1.416 GiB는 GS64 메타데이터의 전치 복사본입니다(투영마다 scales와 biases `[K/64, N]`). unpacked 가중치 복사본은 없습니다. 기존 Q4/Q5 A8 경로도 같은 방식이지만, "상주 증가 0"의 이상에는 미치지 못합니다.
- 임시 활성화 버퍼(Qa, Sa, Ra)는 최대치에서 약 +0.00~0.05 GiB입니다.
- 체크포인트 레이아웃 `[N, K/64]`를 커널이 직접 읽는 실험은 메타데이터 로드가 스칼라가 되어 GEMM이 약 30% 느려졌습니다(`micro_direct_metadata_experiment.jsonl`). 스레드그룹 스테이징 방식은 아직 시도하지 않았습니다.
